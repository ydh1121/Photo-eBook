## What failed

PR #13 replaced the old extraction-based UI library with a custom isolated component renderer. The architecture was cleaner on paper, but it recreated the UI instead of using the existing photo-page component owners.

The user's 56-second browser recording showed severe parity regressions:
- filter labels became `[object Object]` because persisted preview items from the previous data shape were stringified incorrectly;
- top navigation, cards, filters, bottom sheet, device handoff and FAB no longer matched the existing page dimensions and styling;
- preview canvases became much larger than the components, making comparison difficult;
- mobile/desktop proportions drifted;
- the bottom sheet was a management imitation rather than the actual `collection-hub.js` output.

Do not repair that renderer with more CSS patches.

## Correct rebuild direction

Use a reference fixture, not a visual imitation.

Architecture:
`management controller → minimal reference document → existing photo-page/sandbox component DOM + existing JS/CSS owners`

Rules:
- nav markup uses the same `.nav-shell`, `.nav-scroll`, `.nav-chip` structure;
- card rail uses the same `.scroll-row`, `.market-card` structure;
- `collection-hub.js` creates the actual `#collectionLayer`, `#collectionFab`, `#collectionSheet`, `#collectionFilters` DOM;
- bottom sheet tabs are clicked on that same DOM; no clone/reparent/rebuild;
- filter standalone view isolates the actual `#collectionFilters` in place with preview-stage CSS only;
- device handoff uses the actual settings tab accordion generated by the collection runtime;
- `liquid-controller.js`, `chapter-navigation.js`, `rail-drag.js`, `device-handoff.js` remain the behavior owners;
- management-only CSS may position the fixture on a neutral stage, but must not repaint the component skin;
- preview storage remains isolated through the existing sandbox storage isolation layer;
- persisted filter sample data needs an explicit old-shape → string-label migration.
